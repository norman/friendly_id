# FriendlyId

**For the most complete, user-friendly documentation, see the [FriendlyId Guide](https://norman.github.io/friendly_id/file.Guide.html).**

FriendlyId is the "Swiss Army bulldozer" of slugging and permalink plugins. It
lets you create pretty URLs and work with human-friendly strings as if they were
numeric ids.

With FriendlyId, it's easy to make your application use URLs like:

    https://example.com/states/washington

instead of:

    https://example.com/states/4323454

## Which adapter do I want?

As of 6.0, FriendlyId's slug logic is independent of any ORM, and each
persistence library gets its own adapter. FriendlyId itself declares no runtime
dependency on either.

| Your stack | Require | Status |
|---|---|---|
| Rails / Active Record | `friendly_id` (or `friendly_id/active_record`) | All addons |
| Hanami 3.0+ / ROM | `friendly_id/hanami` (or `friendly_id/rom`) | All addons |

Requiring `friendly_id` loads the Active Record adapter whenever Active Record is
available, so **existing Rails applications need no changes**.

FriendlyId 6.0 requires Ruby >= 3.1 and Rails >= 7.1. Hanami users need Ruby >= 3.3,
which is Hanami 3.0's own requirement.

### Hanami and ROM

Hanami's persistence layer is [ROM](https://rom-rb.org), and `Hanami::DB::Relation`
and `Hanami::DB::Repo` are thin subclasses of `ROM::Relation[:sql]` and
`ROM::Repository`, so this adapter works in plain ROM and Sequel applications too.

```ruby
# Gemfile
gem "friendly_id", "~> 6.0"
gem "babosa"          # used to normalize slugs when Active Support is absent
```

Babosa transliterates Cyrillic, Greek, Vietnamese and Devanagari out of the box,
and takes extra rules for languages that romanise shared characters differently:

```ruby
use :friendly_id, base: :title,
  normalizer: FriendlyId::Normalizers::Babosa.new(transliterations: [:ukrainian])
```

Neither babosa nor Active Support transliterates right-to-left scripts. Arabic,
Persian, Urdu and Hebrew produce an empty slug and fall back to a UUID under both
adapters. Override `normalize_friendly_id`, or define an I18n transliteration
rule on Rails, if you need those romanised.

```ruby
require "friendly_id/hanami"

class Posts < Hanami::DB::Relation
  schema :posts, infer: true
  use :friendly_id, base: :title, use: [:sequentially_slugged]
end

# Note the explicit `[:posts]`. Hanami::DB::Repo's root inference does not apply
# to direct subclasses of it, so a bare `< Hanami::DB::Repo` leaves `root` nil.
class PostRepo < Hanami::DB::Repo[:posts]
  include FriendlyId::Rom::Repo

  def find!(slug) = posts.friendly.by_friendly_id(slug).one!
end
```

```ruby
repo.create_with_slug(title: "Hello World")   #=> #<Post slug="hello-world">
repo.create_with_slug(title: "Hello World")   #=> #<Post slug="hello-world-2">
repo.friendly_find("hello-world")             #=> #<Post ...>
repo.generate_friendly_id(title: "Preview")   #=> "preview" (writes nothing)
```

Two differences from the Active Record adapter are worth knowing about, and both
follow from ROM's design rather than from an implementation shortcut:

* **Slugs are never generated by a callback.** ROM structs are immutable and have
  no lifecycle hooks, so there is no `before_save` to hang slugging on. You ask
  for a slug with `create_with_slug` / `update_with_slug`; plain `create` and
  `update` leave the slug column alone.
* **There is no `to_param`.** Pass the slug to your route helpers yourself, for
  example `routes.path(:post, id: post.slug)`.

As on Active Record, `update_with_slug` regenerates a slug only when it is nil,
so editing a title leaves the record's existing URL intact. Ask for a new slug
explicitly:

```ruby
repo.update_with_slug(post.id, title: "New Title")             # slug unchanged
repo.update_with_slug(post.id, title: "New Title", slug: nil)  #=> "new-title"
```

Add a unique index on your slug column. As on Active Record, uniqueness is
enforced by the database, not by the availability check.

#### Slug history

`:history` keeps old slugs resolvable, so renaming something does not break its
URL. It needs a table, and there is a generator for it:

```shell
hanami generate friendly_id   # writes the migration and the relation
hanami db migrate
```

```ruby
class Articles < Hanami::DB::Relation
  schema :articles, infer: true
  use :friendly_id, base: :title, use: [:history], sluggable_type: "Article"
end

repo.update_with_slug(id, title: "New Title", slug: nil)
repo.friendly_find("the-old-slug")   #=> still finds the record
repo.delete_with_slug(id)            #=> removes the record and its slug history
```

`sluggable_type` defaults to the relation name (`"articles"`). Set it explicitly,
as above, to share one table with an Active Record application. Use
`delete_with_slug` rather than a plain delete: the slugs table is polymorphic, so
a foreign key cannot clean it up, and Active Record uses `dependent: :destroy`
for the same reason.

#### Scopes and locales

```ruby
# :scoped takes the column, not an association name
use :friendly_id, base: :title, use: [:scoped], scope: :book_id

# :simple_i18n needs Hanami's i18n, which is not the global I18n
use :friendly_id, base: :title, use: [:simple_i18n], i18n: Hanami.app["i18n"]
```

That `i18n:` option matters. Hanami keeps each slice's locale in a thread-local
and deliberately does not track `I18n.locale`, so without it every slug would go
to the default locale's column.

## FriendlyId Features

FriendlyId offers many advanced features, including:

 * slug history and versioning
 * i18n
 * scoped slugs
 * reserved words
 * custom slug generators

## Usage

Add this line to your application's Gemfile:

```ruby
gem 'friendly_id', '~> 5.5.0'
```

Note: You MUST use 5.0.0 or greater for Rails 4.0+.

And then execute:

```shell
bundle install
```

Add a `slug` column to the desired table (e.g. `Users`)
```shell
rails g migration AddSlugToUsers slug:uniq
```

Generate the friendly configuration file and a new migration

```shell
rails generate friendly_id
```

Note: You can delete the `CreateFriendlyIdSlugs` migration if you won't use the slug history feature. ([Read more](https://norman.github.io/friendly_id/FriendlyId/History.html))

Run the migration scripts

```shell
rails db:migrate
```

Edit the `app/models/user.rb` file as the following:

```ruby
class User < ApplicationRecord
  extend FriendlyId
  friendly_id :name, use: :slugged
end
```

Edit the `app/controllers/users_controller.rb` file and replace `User.find` by `User.friendly.find`

```ruby
class UserController < ApplicationController
  def show
    @user = User.friendly.find(params[:id])
  end
end
```

Now when you create a new user like the following:

```ruby
User.create! name: "Joe Schmoe"
```

You can then access the user show page using the URL http://localhost:3000/users/joe-schmoe.


If you're adding FriendlyId to an existing app and need to generate slugs for
existing users, do this from the console, runner, or add a Rake task:

```ruby
User.find_each(&:save)
```

## Options

### `:allow_nil`

You can pass `allow_nil: true` to the `friendly.find()` method if you want to
avoid raising `ActiveRecord::RecordNotFound` and accept `nil`.

#### Example

```ruby
MyModel.friendly.find("bad-slug") # where bad-slug is not a valid slug
MyModel.friendly.find(123)        # where 123 is not a valid primary key ID
MyModel.friendly.find(nil)        # maybe you have a variable/param that's potentially nil
#=> raise ActiveRecord::RecordNotFound

MyModel.friendly.find("bad-slug", allow_nil: true)
MyModel.friendly.find(123, allow_nil: true)
MyModel.friendly.find(nil, allow_nil: true)
#=> nil
```

## Bugs

Please report them on the [Github issue
tracker](https://github.com/norman/friendly_id/issues) for this project.

If you have a bug to report, please include the following information:

* **Version information for FriendlyId, Rails and Ruby.**
* Full stack trace and error message (if you have them).
